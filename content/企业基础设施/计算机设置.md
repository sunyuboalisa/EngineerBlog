# 一、Windows 11 系统安装

`windows 11` 强制要TPM 2.0以支持安全启动、内存隔离（如HVCI）等安全功能。支持的CPU通常有：

- **Intel**：第 8 代酷睿（Coffee Lake）或更新的 CPU，如 i3/i5/i7/i9-8000 系列及以上346
- **AMD**：Ryzen 2000 系列（Zen+）或更新的 CPU，如 Ryzen 3/5/7/9 2000 及以上（不包括部分 APU 如 2200G 和 2400G）

对于不支持的CPU若需要安装 `windows 11` 系统，可以在制作启动盘过程中绕过该检查。详细步骤如下。
## Step1 系统镜像下载

系统镜像下载渠道有很多，这里在 [xitongku](https://www.xitongku.com/index.html) 上查找需要的镜像。选择 `Windows 11` `24H2` `消费者版` 发布时间根据需要选择。点击 `下载` 后会跳转到下载方式页面，选择适合自己的方式下载镜像文件。例如下载2025年7月更新的：

> zh-cn_windows_11_consumer_editions_version_24h2_updated_july_2025_x64_dvd_a1f0681d.iso

## Step2 启动盘制作

准备容量**8G**以上（建议**16G及以上**）的U盘作为引导系统安装启动盘，使用 **rufus**（The Reliable USB Formatting Utility）工具烧录U盘，项目发布在GitHub上，[点击此处](https://github.com/pbatard/rufus/releases)下载。

打开 rufus.exe 界面如下

![rufus界面](rufus界面.png)

设备选择准备好的U盘，镜像文件选择下载的 windows 11 镜像文件，卷标就是U盘烧录后的名子，可以自定义。其他选项在不清楚含义的情况下建议按图中默认参数设置。之后点击 `开始` 会弹出选项窗口如下

![win11烧录选项](win11烧录选项.png)

重点勾选

> 移除对 4GB+ 内存、安全引导和 TPM 2.0 的要求

其他选项按需勾选。之后点击 `OK` 即可开始烧录，等待烧录完成，取出U盘即完成启动盘制作。

## Step3 安装系统

将需要安装系统的电脑关机，插入启动盘，按下开机键后，连续按下 `F12` 或 `delete` 键（不同电脑型号进入 BIOS 的按键不同，通常为这两个键）。选择启动项为用U盘UEFI引导，之后便进入 windows 11 安装步骤。其中需要注意两点：

1. 若需要输入产品密钥，可以选择 `我没有产品密钥` 来暂时跳过。
2. 在选择系统安装位置和磁盘分区步骤中，谨慎选择格式化的磁盘。若自己之间的文件需要留存，则仅选择原来系统盘格式化。同时一定不要把启动盘格式化（启动盘与机带磁盘的编号不同，例如原本机器上有一块硬盘，会有标记为 `磁盘0`，启动盘会标记为 `磁盘1`）

安装完成后，拔出启动盘，重启计算机，即可进入 windows 11 系统。

## Step4 驱动更新

以联想开天 N80z G1d ZHAOXIN KaiXian KX-U6780A@2.7GHz 系列计算机为例，重装系统后往往需要主动安装核显驱动和蓝牙网卡驱动。

### 核显驱动

前往兆芯官网下载对应CPU和操作系统的驱动，在此例中[点击此处](https://www.zhaoxin.com/qdxz.aspx?nid=31&typeid=555)下载。下载完成后解压，安装时，右击任务栏上的 `开始` 按钮，选择 `设备管理器`，找到 `显示适配器`，右击 `更新驱动程序`，选择 `浏览我的电脑以查找驱动程序`，选择位置为驱动解压的目录，即可完成安装。

### 蓝牙网卡驱动

搜索下载 `BT_AMD-MediaTek`（[直链](BT_AMD-MediaTek_v1.1042.0.499.zip)）和 `WiFi_AMD-MediaTek`（[直链](WiFi_AMD-MediaTek_v3.4.0.1182.zip)），安装方法与上文核显驱动安装方法一致。（还有一个资源，但未验证，就是前往[百度贴吧](https://tieba.baidu.com/p/9082759745)二楼作者回复分享的[百度网盘链接](http://jump.bdimg.com/safecheck/index?url=rN3wPs8te/pjz8pBqGzzzz3wi8AXlR5g1NgdDpM6gxKJDvldXuqyJRM6XowltmJqaiA3XY9m8xJXGEwyoq+4Rai8QM32C0ucU9vjIFH/EszIfqLPJ8IXvcAiHmARy3ObJ2KlfUT6bNq43j0CVPhxVPmZxx/tJaPi7azz+g3ni/+ZYQJtP5582nY9qHh6BM0y)下载）

# 二、离线环境服务器配置VSCode-server

**VSCode Remote-SSH 本质是「带编辑器的远程开发环境」，与Tabby / MobaXterm 等工具不同（其只是「纯终端工具」）**。
## 1. VSCode Remote-SSH 的核心优点

 1. 直接在服务器上**写代码、改配置、看日志**，像在本地一样
> 	打开服务器上的文件夹，就是一个完整项目结构
> 	语法高亮、代码跳转、格式化、重构、查找引用全都有
> 	改配置文件、脚本、日志，体验吊打纯终端
2. 自带终端
> 	VSCode 底部直接开终端，就是服务器的 shell，一边写代码，一边执行命令，一边看日志输出，不用来回切窗口。
3. 插件生态直接搬到服务器
>	Git 图形化
>	代码格式化（Prettier/Black）
>	Lint 检查
>	Docker、数据库插件、REST Client 等，相当于把一整套 IDE 能力带到服务器
4. 调试能力
>	可以**直接在服务器上断点调试**：Python、Node.j、Java、Go等。
5. 上传下载、文件管理更舒服
>	直接拖拽上传
>	右键新建 / 删除 / 重命名
>	像资源管理器一样用，比 sftp 面板舒服得多。
## 2. 离线服务器手动配置 VSCode-server （适用于 2024 年 1.82.0 版本后）

VSCode Remote-SSH 需要服务器安装有配套的 vscode-server，本地使用 VSCode 首次连接互联网环境下的服务器，会自动在服务器上下载对应版本的 server，但在离线环境的服务器上，需要手动配置正确的 vscode-server。

### Step1 查询本地 VSCode 客户端版本

打开 VSCode -> 帮助 -> 关于，记下`提交`（或`Commit ID`）ID 信息。

### Step2 下载对应版本的 vscode-server 程序包

> ！注意：vscode-server 需要与客户端具体的`提交 ID `对应，若有不同用户的 VSCode 客户端`提交 ID `不同，则需要每个提交版本的 vscode-server 同时部署在服务器。

以 Windows 系统服务器需要的 server 下载为例：
浏览器地址栏输入
``` plain text
https://update.code.visualstudio.com/commit:【你的Commit ID】/server-win32-x64/stable
```
和
```
https://update.code.visualstudio.com/commit:【你的Commit ID】/cli-win32-x64/stable
```
分别下载得到 `vscode-server-win32-x64.zip` 和 `vscode_cli_win32_x64_cli.zip` 压缩文件。
### Step3 将 vscode-server 程序包上传至服务器正确的目录

#### step 3.1 在服务器创建目录结构

在服务器用户主目录下的 `.vscode-server` 目录创建目录结构

```cmd
# 创建 .vscode-server 目录结构
mkdir -p .vscode-server/bin
mkdir -p .vscode-server/cli/servers/Stable-${commit_id}/server
```

其中 `.vscode-server/bin` 目录结构是旧版本要求的目录结构，在此仅作保留兼容性用，新版本配置不需要在该目录中存放 server 程序。

#### step 3.2 解压 server 程序
将 `vscode-server-win32-x64.zip` 上传至服务器，并解压在 `.vscode-server/cli/servers/Stable-${commit_id}/server` 目录下

```cmd
tar -xf vscode-server-win32-x64.zip -C "USERPROFILE\.vscode-server\cli\servers\Stable-${commit_id}\server" --strip 1
```

将 `vscode_cli_win32_x64_cli.zip` 上传至服务器，并解压在 `.vscode-server` 目录下。压缩文件中仅有一个 `code.exe` 文件，解压后命名为 `code-${commit_id}.exe`。

```cmd
tar -xf vscode_cli_win32_x64_cli.zip -C "USERPROFILE\.vscode-server" --strip 1

ren "code.exe" "code-${commit_id}.exe"
```

#### step 3.3 创建 lru.json 文件

这一步确保 VSCode Server 能正确识别离线安装的版本，内容为当前已安装的版本数组：
```cmd
# 创建 lru.json 文件
echo ["Stable-${commit_id}"] > USERPROFILE\.vscode-server\cli\servers\lru.json
```

#### step 3.4 最终目录结构验证

```text
%USERPROFILE%\.vscode-server\
├── bin\                          # 旧版兼容目录
│   └── ${commit_id}\             # （可为空，保留结构）
├── cli\                          # 新版核心目录
│   └── servers\
│       ├── Stable-${commit_id}\
│       │   └── server\           # 主程序所有文件
│       │       ├── bin\
│       │       ├── out\
│       │       └── ...
│       └── lru.json              # 版本索引文件
├── code-${commit_id}             # CLI 可执行文件
├── data\                         # 运行时数据（自动生成）
└── extensions\                   # 扩展目录
```


# 三、quartz离线环境部署

本节介绍在离线环境 Windows 服务器如何通过 [[content/企业基础设施/网络#gitea|gitea]]、gitea actions runner 实现 quartz 项目的环境准备、构建，以及 push 后自动部署。

## Step1 部署Gitea

参照 [[content/企业基础设施/网络#Windows 部署|Windows 部署 Gitea]] 节。

## Step2 联网设备准备 Quartz

在联网设备下载 [Quartz](https://github.com/jackyzha0/quartz) 项目源码（这一步建议直接在仓库页下载源码，不下载 Release 中的源码包，仓库页下载的源码布局配置更精致、插件更全面）。

在项目源码目录下，执行

``` cmd
npm i
```

会自动下载项目依赖，完成后会多一个 `node_modules` 文件夹，和更新 `packages-lock.json` 文件。

初始化 Quartz 项目配置

``` cmd
npx quartz create
```

按命令行指引选择并完成项目创建。之后可以尝试开启一个临时服务，预览一下构建好的页面效果

``` cmd
npx quartz build --serve
```

在 [http://localhost:8080/](http://localhost:8080/) 可以预览。

> [!note]
> 根据经验，推荐在构建项目之前，修改一下 `quartz.config.ts` 中关于数学公式渲染的配置

``` config
plugins: {

transformers: [

  Plugin.FrontMatter(),

  Plugin.CreatedModifiedDate({

	priority: ["frontmatter", "git", "filesystem"],

  }),
  
  ...
  
  // 这一行默认是 katex，修改为 mathjax 渲染效果更正常
  Plugin.Latex({ renderEngine: "mathjax" }),
  ],
```

## Step3 创建 git 仓库并推送 Gitea

假设在联网设备上现在的目录为

``` bash
C:\quartz-4
	|  .github
	|  content
	|  docs
	|  node_modules
	|  quartz
	|  .gitattributes
	|  .gitignore
	|  ...
```

则整个 `quartz-4` 文件夹就是完整的 git 仓库，此时运行 `git init` 建立仓库，之后推送到 gitea 远程仓库。注意 `node_modules` 已经在 `.gitignore` 中排除了。

## Step4 服务器安装 Node.js

由于 Quartz 项目是基于 Node.js 构建的（不低于Version 22），因此若要在服务器上构建 Quartz 项目，则需要相应的 Node.js 环境。如果服务器已满足环境要求，则可跳过此步骤。

在 [官网](https://nodejs.org/zh-cn/download) 下载对应的镜像安装即可。

## Step5 服务器构建 Quartz

因为要实现 Action Runner 自动化部署网站，因此构建思路是，在服务器上建立一个文件夹专门用于同步仓库，构建 Quartz。然后利用 Nginx 将构建好的网站定向到 80 端口或某路径。

建立一个文件夹用于同步仓库，例如 `D:\QuartzSite\`，执行

``` cmd
git clone <你的仓库>
```

将联网机之前构建之前下载好的依赖文件夹 `node_modules` 拷贝至 `D:\QuartzSite\` （备用）和 `D:\QuartzSite\你的仓库` 各一份。 ^modulesbackup

进入到仓库目录执行构建命令

``` cmd
cd D:\QuartzSite\你的仓库

npx quartz build
```

构建完成后 `public` 文件夹即是网站目录。

## Step6 配置 Nginx 定向到网站目录

Nginx 在 Windows 系统下的安装和配置不再赘述。修改 `nginx.conf` 配置文件，在 `server` 块中添加如下配置

``` config
http {
    include mime.types;
    default_type application/octet-stream;
    
    sendfile on;
    keepalive_timeout 65;
    
    ...
    
    server {
        listen 80;
        server_name localhost;

        location / {
			...
        }

		# 添加以下两个 location
        location /你要定向的路径名/ {
            alias D:/QuartzSite/你的仓库/public/;
            index index.html;

            try_files $uri $uri.html $uri/ /index.html;

        }
        
        location /你要定向的路径名 {
            return 301 /你要定向的路径名/;  # 自动加斜杠，防止资源找不到
        }
		...

    }
```

当然也可以让 Nginx 监听新端口，此时要添加一个新的 `server` 块：

``` config
http {

	...
	
	server {
		...
	}
	
	# 添加下面新 server
    server {
        listen 8088;
        server_name localhost;  

        location / {
            alias D:/QuartzSite/你的仓库/public/;
            index index.html;

            try_files $uri $uri.html $uri/ /index.html;

        }
    }
}
```

配置好之后开启 Nginx

``` cmd
start nginx
```

> [!note] 常用 nginx 命令
> 
> | 操作          | 命令                      | 说明                                       |
> | ----------- | ----------------------- | ---------------------------------------- |
> | **启动**      | `start nginx` 或 `nginx` | 启动 Nginx（黑框一闪而过是正常的，它会在后台运行）             |
> | **停止 (优雅)** | `nginx -s quit`         | 处理完当前正在进行的请求后，再完整有序地停止服务                 |
> | **停止 (强制)** | `nginx -s stop`         | 立即强行终止 Nginx 服务                          |
> | **重载配置**    | `nginx -s reload`       | **最常用！** 修改 `nginx.conf` 后使用，不用重启即可让配置生效 |
> | **检查配置**    | `nginx -t`              | 修改完配置文件后必做，用来测试语法是否正确                    |
> | **查看版本**    | `nginx -v` 或 `nginx -V` | `-v` 显示版本号；`-V` 显示版本及详细编译参数              |

尝试访问网页，若成功，则可继续进行 gitea-runner 自动化工作流配置。（推荐使用 nssm 将 Nginx 注册为 Windows 服务）

## Step7 配置 gitea-runner

与 GitHub 不同，Gitea 上的 Actions 需要自己在服务器上部署好对应 label 的 runner，并注册到 Gitea 仓库中才能正常工作。

首先下载 [gitea-runner](https://gitea.com/gitea/runner/releases) ，选择 `windows-amd64.exe` 版本的程序。将程序拷贝至 Gitea 服务器，在同目录下执行

``` cmd
gitea-runner.exe generate-config > config.yaml
```

生成默认配置。

修改配置文件中的 labels

``` yaml
  labels:

    # 不要原有的 labels，不然会自动下载 docker，离线环境会失败

    # - "ubuntu-latest:docker://docker.gitea.com/runner-images:ubuntu-latest"

    # - "ubuntu-24.04:docker://docker.gitea.com/runner-images:ubuntu-24.04"

    # - "ubuntu-22.04:docker://docker.gitea.com/runner-images:ubuntu-22.04"
    
    - "windows:host"
```

登录 Gitea 在远程仓库上选择 `设置 -> Actions -> Runners -> 创建 Runner` ，复制下 token。回到 gitea-runner.exe 目录

``` cmd
gitea-runner.exe --config config.yaml register --instance http://你的GiteaIP:端口 --token <刚刚复制的 token>
```

成功后会生成 `.runner` 文件，就是 runner。在远程仓库上也能看到一个 label 是 `windows` 的 runner 状态是 `空闲` 。

## Step8 创建自动部署工作流配置文件

在本地仓库创建 `.gitea/workflows` 目录，创建 `deploy.yml` 文件，内容如下：

``` yaml
name: Build and Deploy Quartz Site

on:
  push:
    branches:
	  # 注意，这里应该填你主干分支的名称，有可能是 main
      - master

jobs:
  deploy:
    runs-on: windows
    steps:
      # 注意：如果目录已存在，git clone 会报错。
      # 如果你的意图是“重置”代码，建议先删除旧目录。
      - name: Clone repository
        run: |

          if exist "D:\QuartzSite\你的仓库" rd /s /q "D:\QuartzSite\你的仓库"

          cd /d D:\QuartzSite

          git clone <你的远程仓库地址>

        shell: cmd

      # 复制依赖：将 node_modules 拷贝进去
      # 使用 xcopy 复制文件夹
      # /E: 复制目录和子目录，包括空的
      # /I: 如果目标不存在，假定它是目录
      # /Y: 禁止提示覆盖
      - name: Copy Dependencies
        run: |
          cd /d D:\QuartzSite
          echo "copying node_modules to 你的仓库..."
          xcopy "node_modules" "D:\QuartzSite\你的仓库\node_modules" /E /I /Y
        shell: cmd

      # Quartz
      - name: Build Quartz
        run: |
          cd /d D:\QuartzSite\你的仓库
          echo "start building..."
          npx quartz build
        shell: cmd
```

之前[[#^modulesbackup|备用的]] `node_modules` 依赖就是在这一步用上的。

将 `deploy.yml` 配置好后，推送到 Gitea 远程仓库，则会自动使用刚刚 label 为 `windows` 的 runner 执行此工作流。

>[!tip] 为什么不用 actions/checkout@v4 之类的工具
> 这种工具是 github 上面提供的，github 还会提供免费的网页 ubuntu 服务器，用于发布 github pages，但这些在自己搭建的离线服务器上都用不了。因此在这个场景下，直接将仓库 clone 出来最直接、最暴力。

> [!tip] 为什么不用 git pull，而是每次都 clone
> 一开始尝试过在 `deploy.yml` 中配置 `git clone` ，但会由于系统用户权限问题失败，因此改为每次都 `git clone`
